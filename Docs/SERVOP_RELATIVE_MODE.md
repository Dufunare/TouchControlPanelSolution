# ServoP 相对离合控制：当前实机恢复基线

**适用仓库和分支**

- 机械臂中转站：`Dufunare/relay_station` 的最新 OpenCV 版 **`master`**（Legacy 8888 → 30003 的 ServoP 已单独开放；v2 运动仍禁用）。
- Windows 控制面板：`Dufunare/TouchControlPanelSolution` 分支 `feat/teleop-6dof-calibration-safe-movl`，PR #3 Draft。
- 控制界面「实体控制模式」默认选 **ServoP · 直接平移跟随**；可以改选 **ServoJ · 逆运动学连续跟随（实验）**。切换模式先停止旧模式，不能让两个模式同时发送运动。

## 设计范围

保持原始 `master` 上已验证可工作的 **33ms ServoP（笛卡尔空间在线跟随）** 思路，并在其上改进可解释的相对映射、断开/暂停/重按的行为、姿态连续性与失效处理。当前 ServoP **只映射平移 XYZ**，不使用 Touch 的旋转操控机械臂姿态；没有要求 Touch 与机械臂工作空间重叠、没有要求绝对空间标定，也不依赖远程 `InverseSolution`。

以第 (k) 次按下 Button1 时采集的 Touch 三维位置 `H_k` 和新鲜 8891 机器人实际六维 TCP 位姿 `R_k` 为基准。默认方向为旧版：

```text
X_target = X_robot_at_press + gain * deadzone(TouchX - TouchX_at_press)
Y_target = Y_robot_at_press - gain * deadzone(TouchZ - TouchZ_at_press)
Z_target = Z_robot_at_press + gain * deadzone(TouchY - TouchY_at_press)
Rx,Ry,Rz = 当次按下时 8891 返回的机器人实际姿态（锁定）
```

其中 `deadzone(d)=sign(d)*max(abs(d)-0.3mm,0)`；用户可在 UI 中改变轴映射、符号及增益（默认 1.0）。**基准不来自 GL 原点、Touch 归零位置、上次按键前的手柄位置，也不来自旧 GetPose 缓存。**

## 离合、模式和失效契约

1. **启动**：先验证 Touch 正常校准、机器人使能空闲、8888/8891 都连通、8891 回包新鲜，随后进入等待 Button1 释放状态。即使启动时按钮已按下，也不会立即运动。
2. **准备**：按钮确实松开，而且观察到连续三个不同 `state_seq` 的机器人空闲反馈后，显示 `[SERVOP READY]`。
3. **首次按下**：在那一帧捕获 Touch 位置、8891 机器人实际 XYZ/RPY，并显示 `[SERVOP CLUTCH]`。**捕获当帧一律不发送 ServoP**；基准点对应零位移。
4. **按住移动**：约每 33ms 计算相对位移、映射为机器人 XYZ，RPY 保持不变。目标每次最多推进 2mm（限制突然跳变）；一个离合按压周期内，目标距本次基准最大 60mm，超限时沿方向截断到这一包络，不会因为移动手柄超过 60mm 立刻 ResetRobot。重复近于相同的目标不会刷指令。根据 8891 验证真实末端跟随。
5. **松开 Button1**：**立即停止产生新的 ServoP**，不把松开期间的 Touch 移动解释成机器人位移。末端仍可能完成最后一条目标；程序等待机器人实际停稳，而不是将停发指令误报为已经静止。松开后超过 1.5s 仍不空闲则请求软件 ResetRobot 并退出本次控制模式。
6. **再按下**：必须先释放并确认连续三个新鲜空闲 `state_seq`，然后在下一次明确的按下重新捕获**当时**的 Touch 和机器人位姿。此后是从机器人**当前位置**继续相对控制，**绝不会追到挪动后的 Touch 绝对坐标或旧基准位置**。
7. **软件工作空间边界**：仅对**本帧**的越界 ServoP 目标拒绝发送，显示 `[SERVOP WORKSPACE HOLD]` 的越界轴、目标值、允许范围及当前实际坐标；不自动调用 `ResetRobot()`，也不自动放大工作空间。保持按住 Button1、将 Touch 朝安全方向移动后，下一条有效目标恢复发送，显示 `[SERVOP WORKSPACE RESUMED]`。发送失败之前不可把拒绝的目标记作“上一已发送目标”，否则会造成反向运动不连续。
8. **模式切换、停止/急停、断线/陈旧反馈、机器人报警、下使能/拖拽、Touch 校准重置、无效姿态、实际 TCP 跟踪偏差过大或真实 TCP 发送失败**：撤销当前离合，终止实体发送；已发运动时申请软件停止。软件停止不等于硬件急停。

## 复测步骤

1. 进入 `relay_station/master`（确认是最新 OpenCV 版本）重新构建、启动。8888 Legacy ServoP 已放行；不要使用旧二进制。此版本同时将 8891 常规 robot_state 输出限制在约 50Hz，保留内部全部 30004 更新及关键状态即时推送，以减轻心跳饥饿。
2. 从控制面板 PR #3 分支重新构建启动。只做 Touch 初始化、8891 反馈确认、平移 Dry Run，确认三个轴的正负方向与预期一致。
3. 在物理急停可用、空旷低速环境下选择 ServoP 模式并手动确认。验证按着 Button1 打开模式时不会直接捕获，松开后得到 `[SERVOP READY]`，再按下得到 `[SERVOP CLUTCH]`；按下当天应无跳变。
4. 保持 1:1 映射做小幅三轴运动；观察 `[SERVOP RATE]` 中实际发送频率、机器人相对基准位移和最新目标误差。对比触觉运动相对差，不比较二者的绝对空间位置。
5. 松开按钮，**把 Touch 挪到远处**。确认机器人没有跟随新 Touch 绝对位置；待 8891 确认停稳后重新按下，查看新的 Touch/机器人基准。再次移动 5–10mm，检查该方向和距离是否正确。
6. 模式选择改为 ServoJ 时，会先停止 ServoP；ServoJ 的 MovL 单步/逆解实验流程仍保留，不与 ServoP 并发发送。

**证据边界**：纯 C++17 离线测试已覆盖首次按下零跳跃、方向、姿态锁定、60mm/2mm 截断、松手不跟随、挪动后重新捕获。CI 不编译完整 Windows Qt/OpenHaptics，现场 ServoP 响应/网络停机和末端准确性仍需独立实机确认。

## 18:31–18:33 现场实测：Y 轴软件边界误停修复

现场已观察到明显 ServoP 实体运动：第一段 `[SERVOP RATE]` 显示相对机器人起点移动 **60.03mm**，8891 反馈 **1ms**、RelayAge **50ms**，说明主要运动链路已经工作。此后多次出现 `ServoP：运动目标发送失败或超出明确工作空间`，但这条旧日志把几种完全不同的故障混在一起。第二、三次的 `[SERVOP CLUTCH]` 起点分别为 `Y=-349.26mm` 和 `Y=-349.79mm`，距离人为配置的 `Ymin=-350mm` 仅有 **0.74mm**、**0.21mm**，因此下一帧向负 Y 方向的目标极容易被软件拒绝。

本轮保持已有的 XYZ 硬边界以及当前坐标映射，不扩展物理工作空间。修改为：工作空间外的**候选**目标显示精确出界维度并丢弃（不发送、不重置），仍允许操作员沿允许方向返回；TCP 断开、发送失败、目标非有限数值仍终止控制。把 `RelativeServoP` 的目标更新从“计算后立即推进”改成“`ServoP` 成功发出后才推进”，确保丢弃的候选目标不造成内部位置漂移。新增纯 C++ 离线回归针对 `Y=-349.79mm` 起点测试阻挡和原离合内的反向恢复。

安全说明：上述 XYZ 数值沿用旧工程的实验用立方体判断，**不是经过认证的 CR3 碰撞/关节/工具工作空间**。在边界附近仍应低速小幅测试。目标拒绝后，已在途的最后一条 ServoP 可能继续执行；应保持独立实体急停可用。若机器人实际越界运动或出现不可预期行为，请停止实机实验，而不是反复尝试或直接调大边界。

## 2026-11-06: 可选扩大相对行程和卡顿诊断（待实机复验）

- **重抓取/离合**：Touch 达到物理边缘时，松开 Button1，待 8891 连续 3 个新状态确认机器人停稳，将 Touch 放回中间，再按下重新捕获当前位置。保持旧版 `X<-Touch X, Y<--Touch Z, Z<-Touch Y` 可选默认映射，支持在启动前换轴和反向；Touch 的位置不用与机器人绝对坐标重合。每次新按下的首帧不发送。
- **增益**：ServoP 的手动映射比例选项现支持 0.05–4.0，默认 1.0；放大倍数与离合范围各自独立，高比例只建议从 Dry Run 和低速小幅验证开始。ServoJ 实验模式入口仍限制 2.0。不能在激活的离合中修改映射配置。

- **卡顿来源诊断**：`[SERVOP RATE]` 新增 `TickGapMax`（控制端回调最大间隔）、`TcpSendAvg`、`TcpSendMax`（控制端同步 sendServoCartesianTarget 调用耗时）。这三项只能判断发送端调度/写入阻塞，不能直接给出指令到物理运动的端到端时延。当前 TCP send 仍在 Qt 回调中同步执行，尚未引入异步发送队列；须先取得数据，再决定是否隔离发送线程。
- **复验顺序**：先保留 1 倍、60mm 跑 Dry Run 与安全范围内的短程操作；再独立测试更大离合范围，最后渐进测试增益。录制 Touch XYZ、目标 TCP XYZ、8891 实际 TCP XYZ、`[SERVOP RATE]`；发生意外运动、异常延迟或指令停发后仍明显持续运动，停止实体测试。
- **证据边界**：新增离线单元测试不等于 Windows Qt 集成编译或实机安全认证。物理急停始终独立可用。

## 2026-11-06 19:36–19:39 现场卡顿与多次自动复位诊断及修复（待实机复验）

日志中四次软件 ResetRobot：19:37:24 feedbackAge=263ms、19:38:43=269ms、19:39:26=280ms 都是 250ms 实时发送门槛的小幅越界；19:37:54 是**待发送候选**目标和实际 TCP 相距 25.70mm 而导致的终止，不是已确认执行失败。其余 WORKSPACE HOLD/RESUMED 均未自动复位。TCP send 最大值约 2.83ms，TickGapMax 58–75ms；后者明显高于33ms名义周期。

本轮新增 ServoP 专用 `ServoPFlowGuard`，不更改 ServoJ/MovL 的权限；保留原有物理风险保护：
- 8891 的 robot_state 年龄在 (250,400]ms，且**会话、User/Tool、机器人使能/模式/错误/拖动状态、8891端口与relay_status仍有效**时，立即停止所有新运动指令、撤销离合，但不因单次轻微门槛越界自动调用 ResetRobot。恢复后仍**不自动继续运动**；必须松开 Button1 并在连续三个新鲜空闲机器人状态后重新按下，重新捕获 Touch/Robot 原点。如果过400ms/显式失联/错误/状态失效，旧有 watchdog/终止策略继续生效。
- 未发送的 ServoP 候选目标与实际 TCP 的误差较大时，启用软阈值 16mm 的 backpressure，不再把**候选目标**的偏差当作机器人的已执行异常；允许能缩小现有跟踪误差的反向纠正，正常恢复须上一已发送目标误差回落到11mm。超过1500ms仍未改善到11mm，或者**上一已发送目标**相对真实TCP偏差超过25mm，仍终止并请求软件 ResetRobot。所有检查保持 8891 实际位置反馈约束。
- UI 的 Touch/GL/状态刷新定时器由8ms放慢为33ms（约30FPS），但OpenHaptics独立高频采样不变，ServoP目标发送定时器仍33ms。此举减少同一Qt线程的绘制负载，不是网络性能提升证据。
- 不变：原 XYZ 工作空间软件限制、单次离合包络、姿态8度偏离、发送后严格跟踪限制、物理急停、明确的离合按键动作。Winsock `send()` 仍同步，未引入会积压过时目标的未经验证异步队列。

注意：静态/离线 C++17 单元测试只能验证状态判定；Windows Qt 集成编译与真机运动效果仍须验收。任何持续运动、TCP反馈错误、异常位姿或真实危险情况均立即停止实验并使用独立物理急停。短时反馈缺口期间执行端可能继续运动最后已收到的指令，所以不要将FEEDBACK HOLD理解成已机械停稳。

## 2026-11-06 19:57: 分离位置增益与跟随速度；机器人位姿反馈预瞄（离线验证中）

现场反馈：手柄快速移动后仍需持续按住、机械臂慢慢追向对应位置。原因是旧控制器将 `scale` 只作用于**目标距离**，随后又把每33ms的目标推进硬限在2mm；提高比例并不改变约60.6mm/s的名义目标追赶速度。此外基于上一已发送目标的16/11mm跟踪等待可能加剧迟滞。

实现修改：
- **位置比例与目标跟随速度分开**：映射增益仍0.05–4.0（默认1x），新控制项 `ServoP 目标跟随速度上限` 默认60.61mm/s，允许选择到120.0mm/s。速度仅指连续目标设定点的变化速率**上限**，不是已经证实的机械臂实际TCP速度/安全工作速度；需要在已验证安全的环境逐步测试。
- **依据实时机器人TCP定位预瞄目标**：每次取最新Touch相对输入，计算期望笛卡尔目标，在正常新鲜8891反馈的前提下，先限制其距**当前实际TCP**不超过12mm，再以可选设定点速度限制其距上次成功下发目标的步幅。这可以避免软件单纯排队慢慢推进一条很远的历史目标，降低目标过远带来的STOP/HOLD概率。没有发出未发送目标的历史队列。
- **仍保留离合行为**：新按键重新抓取基准，松手立即停发；只有通过反馈、工作空间、状态和跟踪门槛时才可能下发目标。前期的250/400ms反馈策略、已发送目标25mm偏差上限、最大180mm离合范围和XYZ实验界限保持不变。
- **物理效能限制**：机器人的ServoP实际执行频率、线速度、控制器内部平滑/排队延迟及中转站转发耗时尚未实测，不能通过加比例或设定点速度就保证真机无延迟。急停/停机路径必须始终独立可用；本方案不是认证的动态速度/加速度限制器，暂不声称安全的高速遥控能力。

验证：新增C++离线回归覆盖4倍位置增益下单独提高速度、实时TCP预瞄12mm上限、松手重抓取和触控反转（仍待Windows/机械臂验证）。

## 2026-11-06 诊断：速度依然低，先区分软件节流与机械执行

这次反馈指出：即使上轮将软件设定点推进上限开放到120mm/s，并采用机器人实际TCP附近的12mm预瞄，实际跟随仍慢。这说明存在至少两个独立的潜在瓶颈：**(a) 发送端软件设定点限速/预瞄/TrackingHold**，或 **(b) 中转站与控制器内部 ServoP 插值、命令接受或机械运动速率**。当前没有同时记录足够的速度指标，不能把其中某一种当作已证实根因。

本轮**仅增加非控制性的诊断**，避免在不知道控制器实际接收/执行速度及工作空间安全性时继续放大实体目标速度：

- `[SERVOP FOLLOW]`（约每2s）：`8891实际TCP路径速度` 按不同 `state_seq` 实际 TCP 相邻位姿距离累计；`已发送设定点路径速度` 按已成功本地TCP写入的相邻目标距离累计；`FeedbackLead限幅` 表示期望目标被12mm预瞄裁剪的次数；`TrackingHold帧` / `WorkspaceHold帧` 是发送受保护逻辑限制的次数；`速度上限` 是软件设定点速度限制。以上均为各统计窗口内**路径长度/时间**，不是固定轴位移、机器人瞬时速度、远端接收确认或电机实际速度。
- `[SERVOP RATE]` 仍保留 TCP 写入耗时、控制Tick峰值间隔、反馈年龄、已发目标与实际TCP误差等。
- 所有诊断计算采用纯 C++17 无Qt/设备依赖的 `shared/ServoPFollowMetrics.h`；不修改 ServoP 指令格式、不提升实体速度、不改变硬性空间边界或 ResetRobot 停止条件。只有反馈有效且离合已激活时才采样统计。
- 若 `已发送设定点路径速度` 持续接近设定上限、但 `实际TCP路径速度` 明显更低且反馈仍新鲜，优先检查控制器内部在线轨迹、固件支持的参数和真实运动限制。若已发设定点速度本身很低，或某种Hold大量出现，则先优化客户端限流/映射。若 `TickGapMax` 高而 TCP 写入时间低，则优先隔离Qt事件循环中的运动控制与绘制线程。
- 控制器协议资料可能提及 `ServoP` 可选的 `t/aheadtime/gain` 等，**未验证当前实验室控制器固件的支持情况**，本轮不得直接启用或猜测这些参数值，也不得把缩短插值时间等同于机器人具备更高的安全运动能力。

测试仍限于离线规则和统计函数，现场应保持独立物理急停、工作空间无人，先采集一次安全短程实验的连续三个或更多统计窗口，再设计下一步控制器与软件性能优化。
